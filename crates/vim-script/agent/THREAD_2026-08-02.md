# Vimscript Runtime Agent Thread — 2026-08-02

> Durable engineering record of the current agent thread. This is a structured thread summary rather than a byte-for-byte UI transcript; it preserves the requests, decisions, implementation outcomes, validation, commits, and pending work needed to continue development.

## Project goal

Build a robust, embeddable Vimscript interpreter/runtime in Rust with:

- Legacy Vimscript compatibility first
- Lexer → parser → AST → resolver → bytecode → VM pipeline
- Explicit asynchronous suspension
- Host-agnostic editor APIs
- Capability enforcement
- Ex commands, mappings, options, and autocommands
- Compatibility tests against Vim
- Incremental support for real plugins

## Initial architecture

The project began as an empty Rust binary. The implementation was organized into these modules:

- `source`: source files, spans, and diagnostics
- `lexer`: Vimscript tokenization
- `parser`: expression, statement, and Ex parsing
- `ast`: typed syntax tree
- `resolver`: scopes, symbols, bindings, and captures
- `compiler`: AST-to-bytecode compilation
- `bytecode`: instructions, constants, and function prototypes
- `runtime`: values, builtins, VM, scheduler
- `host`: async host and command boundaries with capabilities
- `integration`: options, mappings, and events
- `plugin`: runtime paths, script loading, autoload, reports
- `mock_editor`: reusable editor host for integration tests

Canonical Vim help references and selected Vim regression files were downloaded into `references/`.

## Plugin step 1: module-owned function references

Problem:

`FunctionId` is module-local. A closure loaded by one script could not safely execute in another VM module.

Implemented:

```rust
pub struct FunctionRef {
    pub module: Arc<BytecodeModule>,
    pub function: FunctionId,
}
```

Call frames now retain the owning module. Constants, spans, nested closures, and stack traces resolve against the frame module.

Regression proof:

- `first.vim` exports a function reading its own `s:` value
- `second.vim` invokes it
- The function returns the first script’s value, not the caller’s

## Plugin step 2: automatic autoload

Implemented:

- Unresolved `name#part#function` symbols resolve lazily
- Compiled modules are scanned for autoload references
- `demo#util#answer()` maps to `autoload/demo/util.vim`
- The file is loaded before caller execution
- Module-owned closure is merged into shared globals
- Missing files report `CompatibilityStage::Discovery`

Current boundary:

- Static bytecode references are discovered across all compiled functions
- Fully dynamic function-name construction remains future work

## Plugin step 3: `exists()` and load guards

Implemented VM-aware `exists()` support for:

- `g:` variables
- `s:` variables
- Builtins and functions (`*name`)
- Environment variables (`$NAME`)
- Missing names

Added namespace dictionary snapshots such as `g:` so this works:

```vim

```

Conventional guard verified:

```vim

  finish
endif
```

Differential fixture matches Vim 9.2.

## Plugin step 4: source-preserving Ex parser

Added `ExLineParser`, which parses directly from original source and preserves:

- Leading `:`
- Modifiers
- Ranges and addresses
- Command name and bang
- Exact raw arguments
- Unescaped `|` separators
- Remaining command source

Supported address forms include line numbers, `.`, `$`, `%`, marks, searches, and offsets.

Important limitation:

This parser understands the Ex command envelope, not every command-specific grammar. Specialized parsers are still required for commands such as `substitute`, `global`, and compact forms like `:1,2dd`.

## Discussion: ranges and compact delete

The parser understands the range in:

```vim
:1,2dd
```

but currently sees command name `dd`. Full support needs:

- Canonical Ex command definition table
- Prefix-aware splitting (`d` → `delete`)
- Delete-specific compact register parsing (second `d`)
- Runtime address resolution against editor state
- Register storage and buffer deletion

## Regex discussion and decision

Regex enters through:

- `=~`, `!~`
- `match*()` builtins
- `split()` and `substitute()`
- `:substitute`, `:global`, searches
- Syntax files

Vim has its own regex dialect. Directly passing Vim patterns to Oniguruma would not be compatible because of constructs such as:

- `\v`, `\V`, `\m`, `\M`
- `\c`, `\C`
- `\zs`, `\ze`
- `\<`, `\>`
- Vim lookaround notation
- position atoms and newline atoms

Recommended future architecture:

```text
Vim regex parser → regex AST → Oniguruma/backend translation → Vim semantic wrapper
```

Decision for now:

- Reserve regex for a later dedicated phase, potentially its own project/crate
- Do not block external-plugin selection on full regex
- Select a small plugin with minimal or no regex usage
